## Agent rules block

The first block is the project's own sample prompt, copied verbatim from `CONTRIBUTING.md` (nine
rules until 26 Nov, ten now). The project asks agent users to put it in the agent's instructions. The
addendum adds what that sample leaves to the human contributor, and condenses the conventions from
`.agents/skills/contributing`. Paste both, in this order.

```text
You are contributing to x402, an open protocol for internet-native payments.
x402 handles real value transfer — correctness is critical.

Follow these rules for all code, documentation, and commit messages you produce:

1. CONCISE OUTPUT ONLY. Do not add filler comments, redundant docstrings, or
   verbose explanations. Every line of documentation or commentary must carry
   useful information.

2. NO REDUNDANCY. Do not generate duplicate or near-duplicate code, tests, or
   explanations. If logic already exists, use it — do not rewrite it. Three
   similar lines are better than an unnecessary abstraction, but three identical
   blocks are never acceptable.

3. VERIFY AGAINST THE SPEC. Before writing payment, signing, or settlement
   logic, read the relevant spec in specs/. Do not invent header names, payload
   fields, or signing flows. If you are unsure whether a field or constant
   exists, search the codebase — do not guess.

4. MATCH EXISTING PATTERNS. Read the surrounding code before generating new
   code. Match the style, naming conventions, error handling, and test patterns
   already in use for that SDK (TypeScript, Python, Go, or Java).

5. DO NOT ADD UNREQUESTED FEATURES. Implement exactly what was asked. Do not
   add extra configuration options, feature flags, helper utilities, or
   "improvements" beyond the scope of the task.

6. COMMIT MESSAGES. Use conventional commits (feat:, fix:, docs:, chore:).
   Keep the subject line under 72 characters. The body should explain why, not
   what — the diff shows what changed.

7. CHAIN AND TOKEN CONSTANTS. Never hardcode chain IDs, token addresses, or
   decimal values from memory. Always reference the constants defined in the
   codebase (e.g., mechanisms/<family>/constants for chain IDs and ABIs,
   mechanisms/<family>/default_assets for USD-pegged token defaults).

8. TEST CORRECTNESS. Generated tests must assert meaningful behavior, not just
   that "the function doesn't throw." Do not fabricate expected values — derive
   them from the spec or existing test fixtures.

9. COMMUNITY CHANNELS. GitHub issues are for bug reports and concrete feature
   proposals only. Direct questions, general discussion, and project showcases
   to the x402 Slack community at http://slack.x402.org/.

10. READ THE SKILLS. Before writing code or specs, read
    .agents/skills/contributing and .agents/skills/authoring-specs. They summarize
    conventions maintainers check in review.
```

```text
x402 addendum (from CONTRIBUTING.md, the PR template and .agents/skills/contributing):

11. SCOPE. Each change touches one SDK and one concern. NEAR work lives in
    typescript/packages/mechanisms/near and specs/schemes/exact/scheme_exact_near.md.
    Never modify core packages for a mechanism change. Never edit legacy/v1 code
    (typescript/packages/legacy, go/legacy, python/legacy, java/): frozen, security
    patches only.

12. CHANGELOG FRAGMENT for every user-facing change: TypeScript
    `pnpm -C typescript changeset` (publishable @x402/* packages only), Go
    `make -C go changelog-new`, Python a towncrier file in python/x402/changelog.d/.
    Mark breaking changes with a **Breaking** line. Docs-only changes skip it.

13. BEFORE HANDING BACK: TypeScript `pnpm format && pnpm lint && pnpm build && pnpm test`
    from /typescript; Python `uvx ruff format && uvx ruff check` and `uv run pytest`
    from python/x402; Go `make fmt && make lint && make build && make test` from /go.
    Paste the real output.

14. A TEST THAT PROVES THE FIX. A bug fix ships with a test that fails without
    the fix. Show it failing (a baseline run or a mutant) and passing. No tests for what
    the type system already guarantees or that only restate constants; cover edge cases.

15. DO NOT TOUCH the paywall generated templates unless the change is to the
    paywall; if it is, regenerate them with the CI steps in CONTRIBUTING.md.

16. FIND A DEMONSTRATED PROBLEM. Reproduce the issue on current main first. Hardening,
    diagnostics or options without a demonstrated problem are not merged. Duplicates are
    closed: if an open PR already covers it, stop and report it.

17. SDK CONVENTIONS. Same payload, same outcome in TypeScript, Go and Python. Error and
    reason codes are a wire contract: never rename one. A facilitator answers malformed
    client input with isValid:false and a stable reason, never an HTTP 5xx. New options keep
    today's behaviour as the default. No new hard-coded RPC endpoints. No imports of
    mechanism packages in core.

18. NEUTRALITY AND COMMENTS. No references to a specific facilitator, vendor or
    third-party service in code, docs, examples or e2e tests. Write "onchain". Comments
    describe this SDK's current behaviour only: no other SDKs, commits or issue numbers,
    no narration of work in progress.

19. PR DESCRIPTION. Short, matching the diff: what and why, linked issues, root cause in
    one paragraph citing file and line. Every commit signed. No binaries, planning notes or
    unrelated lockfile changes. Resolve conflicts with main before review.
```

## Orchestrator notes

| Item | Rule |
|---|---|
| PR title | Conventional, lowercase after the colon, at most 72 characters. Example: `fix(near): ...`. |
| PR body | The template's `## Description`, `## Tests` and `## Checklist` sections, plus a short `## AI assistance` section. Since 26 Nov: root cause in one paragraph with file and line, design tradeoffs when there was ambiguity. |
| Draft | Open as Draft. CONTRIBUTING says not to open a non-Draft PR until a human has reviewed the AI output. The operator's review at the gate is that review, and only after it does the PR go to Ready. |
| Signing | Required for merge. Run `signed_check.py --repo x402 --pr N` after every push. |
| AI disclosure | Required when most of the PR is AI-generated, which is always true for us. One plain sentence, e.g. "Most of this change was written with Claude Code and reviewed by me." |
| Volume | "Do not batch-generate low-effort PRs." At most one new x402 PR per day, and only after the previous one has had a maintainer response. Since 26 Nov also: hardening or diagnostics without a demonstrated problem are not merged, duplicates are closed, and inactive PRs are closed (to resume, ask in the closed PR). |
| Before any x402 agent | The agent reads `.agents/skills/contributing/SKILL.md` and `.agents/skills/authoring-specs/SKILL.md` on current `main` first (rule 10); `main` was c1006950 on 2026-11-27. |
| CI | `ci.py dispatch --target KhomDev/x402 --toolchain node --command 'cd typescript && pnpm install --frozen-lockfile && pnpm --filter @x402/near test'` (check the filter name in `typescript/packages/mechanisms/near/package.json`). |
| Known red check | Vercel fails on fork PRs because the Coinbase team has to authorise them. It is not ours to fix: say so if asked, never re-run it. |

## Lessons from our PRs

- The reviewers (IkerAlus, phdargen) read every line. A wording fix in a changeset counts as much as
  a code fix.
- An expiry or replay concern raised in review gets a test with a mutant: the mutant fails, the fix
  passes.
- Since 26 Nov a maintainer-run skill file lists what reviewers check (SDK parity, wire-contract error codes,
  neutrality, no hard-coded endpoints). Check a draft against it before the gate, not after review.
